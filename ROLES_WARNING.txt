WARNING: local patches applied to vendored Galaxy roles
========================================================

The following files inside ansible/roles/ are vendored (installed via
`ansible-galaxy role install -r requirements.yml`) but have been
LOCALLY PATCHED to work around upstream bugs. Re-running the galaxy
install for these roles with --force (or deleting/reinstalling the
role directory) WILL SILENTLY DISCARD these patches.

Do not run `ansible-galaxy role install -r requirements.yml --force`
for the roles below until the upstream bug is confirmed fixed. If you
do need to reinstall, re-apply the patch (or check upstream first) and
remove that role's entry below.

To install/upgrade a SINGLE role from roles/requirements.yml (e.g. to
bump albancrommer.formations_quiz to a new release) without touching
the patched roles below, do NOT run the plain `-r requirements.yml`
install -- it installs everything in that file. Instead:

    cd ansible/roles
    cat > /tmp/single-role.yml <<'EOF'
    roles:
      - name: <role_name>            # must match the name: in requirements.yml
        src: <src_from_requirements.yml>
    EOF
    ansible-galaxy role install -r /tmp/single-role.yml -p . --force

`-r` requires the file to end in .yml/.yaml (a heredoc piped to
/dev/stdin will be rejected), and `name:` matters: installing straight
from a bare tarball URL (no requirements file, no name:) lets
ansible-galaxy derive the install directory from the tarball's own
internal layout instead of the name you want -- e.g. installing
albancrommer.formations_quiz's v0.9.0 tarball without a requirements
file landed at ansible/roles/albancrommer.formations_quiz-0.9.0/
instead of ansible/roles/albancrommer.formations_quiz/, breaking every
playbook/role reference to it. Only a requirements file lets you pin
the install directory name explicitly.

Role: xanmanning.k3s
File: ansible/roles/xanmanning.k3s/vars/main.yml (line ~151)
Patched: 2026-09-19

Upstream bug: `k3s_ensure_directories_exist`'s "Private registry config
file" entry chains `| dirname` after `default(omit)`:

    path: "{{ (k3s_runtime_config['private-registry'] | default(omit)) | dirname }}"

When k3s_runtime_config has no 'private-registry' key (the common
case, and ours), default(omit) produces Ansible's internal _OmitType
sentinel, which the dirname filter then chokes on:

    [ERROR]: The filter plugin 'ansible.builtin.dirname' failed:
    expected str, bytes or os.PathLike object, not _OmitType

Fixed locally by routing through default('') first so dirname always
receives a real string, then omitting the item if empty:

    path: "{{ (k3s_runtime_config['private-registry'] | default('') | dirname) or omit }}"
